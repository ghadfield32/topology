Three defects this run exposed, and their fixes

These are the reason the numbers above are trustworthy; the earlier ref01–ref05 directories were discarded rather than reinterpreted.

  1. Blank memory in the planner. Every candidate plan forked from a zeroed GRU state. Because the observation hides the velocities, a blank memory cannot know the cart is moving, so planning degenerated. Fixed with advance_memory: fold each real observation and shove forward, then fork. Measured effect: 176 steps versus 51 for the retained broken policy.
  2. Blank memory in the drift measurement. The same mistake in free_rollout_errors made the first predicted step a pure guess, so the model lost to the frozen baseline at depth 1 for reasons that were not drift. Fixed by warming the memory with the same number of real transitions (memory_warmup_steps, recorded).
  3. Zero crash positives in training. valid_window_starts used end - sequence - 1, which drops the final transition of every episode — the only transition that can carry a terminated label. Measured: 0 positives in 7,906 windows. Fixed to end - sequence, and the dataset now records next_observations explicitly so the labelled transition always has a prediction target. A test asserts a positive is present.

Four more defects, found by auditing the finished code against its own claims

These were not caught by a test failure. They were caught by asking the six questions in docs/release/VERIFICATION.md about the code that already passed its suite. That is the honest order: a green suite is a statement about the tests, not about the experiment.

  1. Goals were scored in normalized units against a metric target. PARK_TARGET is 1.0 metres, but score_park compared it against a normalized observation, where 1.0 means 2.4 m. The planner was asked for the rail limit while the constant said one metre. Fixed by converting to metres first, with a test asserting that a dream ending exactly at the target scores 1.0 and one metre off scores 0.0.
  2. Predicted failure was not absorbing. survival_mask applied a per-step threshold, so a dream could crash at step 3 and be scored alive at step 4 — making a doomed plan look survivable. Fixed with a running logical AND, plus a test on a [-1, +5, -1, -1] dream.
  3. Rollout error was averaged over depths. free_rollout_errors averaged steps 1..h, which answers "how wrong on average" and hides the depth where the model falls apart. Fixed to report error at depth h, which is what changed the headline result from "9 within tolerance, 8 beating frozen" to the article's actual finding: 7 within tolerance, 29 beating frozen.
  4. The best checkpoint was logged but not restored. train() recorded the best validation epoch and then left the final-epoch weights in the model, so every later measurement described a different model from the one the reported loss belonged to. Fixed with load_state_dict on a saved copy; the restore is now recorded as restored_best_epoch.

Question 6 in the audit list — "does evaluation use the selected model checkpoint?" — is exactly defect 7. The answers are now asserted rather than intended: test_goal_is_scored_in_physical_units_not_normalized_ones, test_predicted_failure_is_absorbing, test_rollout_error_is_reported_at_depth_not_averaged_over_depths, and test_training_restores_the_best_validation_checkpoint.

A correction to the loss, not just the code

The article's "count each crash 380 times over" was first implemented as 380 * BCE(...). That scales the loss and its gradient but leaves the optimum at the 99.4% base rate, so the head still answered "always alive" with confidence. The correct form is pos_weight=380 inside the BCE, which moves the optimum. The two heads also differ in natural scale by about four orders of magnitude, so TERMINATION_LOSS_SCALE is declared and recorded. Measured on a smaller 60-episode run: scale 0.01 gave 0.38 recall, 0.02 gave 0.93 with the delta error unchanged, 0.10 gave 0.81. The default is 0.02.

The cross-language parity check

uv run --no-sync python -m pytest -q tests/test_world_model_ladder.py

Observed: 16 passed. The important one runs both ladders on the same configuration and compares their saved records: exact equality for counts and coefficients, 1e-9 for floating-point results.

It found two real bugs, which is the entire argument for writing the second implementation:

Bug Symptom Why only a second implementation found it
x ** 2 in Python vs x * x in Rust 1 ULP differs for ~0.06% of doubles chaos amplifies it into a visibly different trajectory within a long episode
signed theta in Python's score vs theta.abs() in Rust Python's best "balance" plan scored 1.048; Rust's 0.993 Python rewarded a pole leaning one way, so its best plan was to fall over

Both are fixed, and both now carry a comment saying why the code is written that way.

What was not executed here

  • No GPU run. No CUDA path, no mixed precision, no timing comparison with the article.
  • No DQN baseline. The comparison agents are coin flips, the hand-written controller, and the frozen-state model.
  • No reproduction of the article's figures or numbers. See SOURCE_AUDIT.md for the exact list of the author's measurements that are quoted rather than re-measured. In particular the article's "H = 29", "37 steps" in front of the frozen baseline, "500.0 ± 0.0", "2.94 ms" and "one step in 380" are the author's numbers under the author's configuration. Ours are 7, 29, 176.0, 10.3 ms and about 1 in 187 (from collected episodes).
  • No ruff/black/pylint run. Those are the Python equivalents of fmt and clippy and they are not installed in this environment. Their absence is blocked, not passed; the repository's Python suite is the gate that actually ran.
  • No --release build for either Rust crate. Only cargo test --offline --locked, cargo run --offline, cargo fmt --check and cargo clippy --all-targets -- -D warnings.
  • No Go implementation. Not every companion needs three languages; this one is Python and Rust because the point is a scientific reference plus a checkable core.
  • No learner assessment. assessment is not_assessed in every record, and EXERCISES.md and LADDER.md leave the independent work to the learner.

Scope of these results

These are numbers from one configuration and one seed on one machine under simultaneous external load. They show this pipeline runs, that the two persistence implementations agree, and that the disclosed bug is real and measurable. They do not show that a world model is a good idea for any real robot, that the planner is competitive with a tuned policy, or anything about a learner.
