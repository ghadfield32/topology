Notebooks: one lab, three languages

Every one of the 57 native16 learning units now has an interactive notebook in Python, Go and Rust — 171 notebooks in total. This answers the question "can I learn this in any language?" with a concrete, runnable route.

Index: workbooks/polyglot/index.html (plain text: README.md).

Every notebook opens with a path legend

The notebooks sit three levels deep, so a root-relative path in prose is a dead link. Each notebook therefore starts with a "Where every path points" cell that defines the shared vocabulary once:

  • the owner files (curriculum/catalog.json, native/protocols/labs.json),
  • the course folders (lessons/, notebooks/, practice/),
  • the native folders (native/go/, native/rust/, native/python/, native/guides/),
  • the tooling and generated paths (tools/, workbooks/polyglot/),
  • my_work/ as yours,
  • the reference-vs-your-copy distinction,
  • and the relative links to the other two languages, the index, and the guides.

A test asserts that every markdown link in every notebook resolves from that notebook's own directory, and that the legend defines the paths it mentions. This guards a real regression: the lesson link used to be emitted as lessons/01_lesson.md, which cannot resolve from workbooks/polyglot/<lang>/ (57 broken links, now 1308 resolving links and zero broken).

Repository-wide definitions live in REPOSITORY_LAYOUT.md.

Where things live (this is the usual point of confusion)

Several folders contain Go or Rust material, and they are not the same thing:

Path What it is Do you edit it?
workbooks/polyglot/python/ notebooks that run the canonical Python reference no
workbooks/polyglot/go/ notebooks that run the real Go program no
workbooks/polyglot/rust/ notebooks that run the real Rust program no
native/go/, native/rust/ the reference source those notebooks compile no — read-only reference
my_work/<session>/native/go\|rust/ your copy from native_course.py prepare yes — here
notebooks/, lessons/, practice/ the original course labs and assignments your learner notebook

notebooks/ is the original course. It has no go or rust folder and does not contain these notebooks. The 171 notebooks live under workbooks/polyglot/; each language folder has its own README.md so it is self-guiding when opened.

For Stage 01 the three notebooks are:

workbooks/polyglot/python/stage01.ipynb
workbooks/polyglot/go/stage01.ipynb
workbooks/polyglot/rust/stage01.ipynb

The three notebooks do different jobs

Route Notebook What it actually does
Python workbooks/polyglot/python/<lab>.ipynb Runs the canonical Python reference in a fresh kernel inside an isolated copied workspace, then audits the registered inputs and resolves a specific native run's outputs.
Go workbooks/polyglot/go/<lab>.ipynb Checks the toolchain, shows the actual dispatch arm in native/go/engine/labs.go, compiles the Go program, runs only this lab, prints its metrics, and verifies input hashes.
Rust workbooks/polyglot/rust/<lab>.ipynb Same, for native/rust/src/labs.rs, plus the pinned-toolchain and ownership notes.

The Go and Rust notebooks end by comparing against the other language using the runner's own tolerance rules (1e-8 absolute, 1e-7 relative) and checking that both languages recorded identical input hashes.

The Python route runs the real original experiment

The Python notebook calls shape_lab.course.run_references(ROOT, [reference], out, jobs=1, timeout=300) — the same execution path the course itself uses. It gets a fresh kernel, an isolated copy of the source, a runtime provenance probe, and allow_errors=False. It is not a lookalike calculation and it is not a Python re-implementation of the native unit.

The reference is not always a notebook. The Poux lab's canonical reference is a script (curriculum/extensions/poux_spatial_ai/bridge.py), so it is labelled script and its companion test is run instead of pretending it is a notebook. A test asserts that a script lab is never handed to run_references.

Sections are labelled by intent

The Python notebook separates three things, and says which is which:

  1. Run the canonical Python experiment — the original course material.
  2. Input audit — which registered files this lab consumes, and their hashes.
  3. Output audit — reads an existing native run; it does not recompute the lab.

The native experiment itself runs in the Go and Rust notebooks.

Evidence is resolved explicitly, never by "newest file wins"

tools/evidence_pointer.py resolves which run a reader should look at:

  1. an explicit run_dir,
  2. my_work/native_evidence.json (written by evidence.write_manifest),
  3. otherwise nothing in strict mode.

The Python notebook exposes this as two explicit modes, set at the top of its evidence cell:

Mode Behaviour
MODE = "fresh" (default) creates the evidence now by compiling and running the native Go and Rust labs into the notebook's own run directory, then verifies its identity. Nothing older is used.
MODE = "review" opens a specific previous result from PINNED_RUN and labels it as previous execution. PINNED_RUN is required; there is no scanning fallback.

Neither mode silently chooses the most recent plausible folder. Runs now record an identity block in execution.json, so stale evidence cannot masquerade as current.

What these notebooks deliberately do not do

  • They do not compute the science in Python. A test asserts the Go/Rust notebooks never import NumPy/Torch/SciPy/sklearn and always call runner.build(...) and runner.execute_lab(...). Python is the driver only.
  • They are not a second curriculum. curriculum/catalog.json still owns the 31 stages; the notebooks carry no catalogue of their own.
  • They do not grade you. Every notebook is not_assessed, and each one keeps its lab's stated boundary ("what this lab does not establish").
  • They do not claim original-notebook parity. That remains not_certified; see native/COVERAGE.md.

Run them

In VS Code, open any notebook under workbooks/polyglot/ and run the cells top to bottom. Or from the command line, from the repository root:

$env:PYTHONUTF8 = '1'
uv run --no-sync jupyter lab

Or execute headless (this is how they were verified):

uv run --no-sync jupyter nbconvert --to notebook --execute `
  --output-dir my_work/notebook_run `
  workbooks/polyglot/python/stage01.ipynb

The Python notebook needs an existing native run to have something to read. The first time, create one:

uv run --no-sync python native_course.py compare --lab stage01 --output my_work/notebook_stage01_first01

The Go and Rust notebooks build what they need themselves and write to my_work/notebook_<lab>_<language>/.

The full 171-entry sweep is run by tools/verify_language_notebooks.py, which derives the expected set from the registry, uses fresh kernels and explicit working directories, compiles each native binary once per source identity, runs serially, preserves failures, rejects missing/duplicate/stale entries, and returns non-zero unless coverage is complete. There is no flag to tolerate errors, and partial runs report coverage.complete = false. Observed full sweep (my_work/nb_verify_full03/coverage.json):

A "verify" result is not the same claim as "three smoke notebooks ran". See the sweep's coverage.json for the actual counts and every failure record.

Regenerate

The notebooks are generated, not hand-edited, so they stay consistent when the lab catalogue changes:

uv run --no-sync python tools/build_language_notebooks.py

Verify without writing anything:

uv run --no-sync python tools/build_language_notebooks.py --check

--check exits non-zero and names every missing, stale or unexpected artifact. It genuinely can fail: deleting an artifact, editing one by hand, or adding an unregistered notebook all make it return 1. Unknown flags are now a hard error rather than a silent full rewrite.

Then run the test above; it fails if the committed tree is stale. The generator is tools/build_language_notebooks.py and reads native/protocols/labs.json plus the existing native_course.py runner API — no new dependency is added.

Do not regenerate while a verification sweep is running. The sweep hashes the whole notebook tree before and after, and reports coverage.complete = false if it changed, precisely so a mixed-source result cannot look green. Regenerate first, then sweep.

Boundaries that remain

The untested gates from the native import still stand: the 133 original notebooks were not replayed, and Docker, Kubernetes, macOS, GPU and the remote CI workflows did not execute here. These notebooks are a convenience layer over the same native16 evidence, not extra certification of it. See NATIVE16_IMPORT.md.
